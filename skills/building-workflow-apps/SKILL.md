# Building Whippy Workflow Apps

For AI coding agents and developers with **no Whippy monorepo access**. Everything runs against the hosted platform at `https://workflows.whippy.ai` using the public [`ww-cli`](https://github.com/hellowhippy/ww-cli).

Companion human docs (public repo — links stay valid after copying only this skill folder):
[Getting started](https://github.com/hellowhippy/ww-cli/blob/main/docs/GETTING_STARTED.md),
[Best practices](https://github.com/hellowhippy/ww-cli/blob/main/docs/BEST_PRACTICES.md).

---

## 1. What you are building

Whippy has a visual **workflow builder**. A **workflow app** is a TypeScript package that exposes a third-party API as steps in that builder. It compiles to `app.json` plus a Cloudflare Worker bundle. The platform invokes handlers with `{ "function": "<dot-path>", "bundle": { ... } }` (e.g. `creates.send_message.operation.perform`).

| Kind | Purpose |
|------|---------|
| **searches** | Reads / lists / lookups. Also feed **dynamic dropdowns**. |
| **creates** | Mutations (create / update / delete / send). |
| **triggers** | Webhook entry points. |

Users: add an App step → connect an account → pick an action → fill Config (from your `input_fields`) → map outputs via `${step_alias.output.data…}`. Accurate `sample` and `output_fields` matter.

**Prerequisites:** Whippy account + API key (create/copy under **Developers → API keys** at [https://app.whippy.co/developer/keys](https://app.whippy.co/developer/keys)), Node.js, `ww-cli` (`cargo install --git https://github.com/hellowhippy/ww-cli --locked`), vendor API docs (OpenAPI preferred).

## 2. Agent CLI permissions (mandatory)

**Agents test; humans deploy.**

| Command | Agent | Notes |
|---------|-------|-------|
| `ww-cli build` | Yes | After meaningful code changes |
| `ww-cli validate` | Yes | Necessary, not sufficient vs server |
| `ww-cli invoke` | Yes | Needs build + real creds in `test-data.json` when testing live |
| `ww-cli test` | Yes | If `package.json` defines `test` |
| `ww-cli push` / `push --create` | **No** | Unless user explicitly asks |
| `ww-cli promote` | **No** | Unless user explicitly asks |
| `ww-cli make-global` / `login` / `secrets set` | **No** | User-owned |

When build + validate + at least one invoke succeed, **stop** and tell the user to run `ww-cli push` / `promote`.

### Core loop

```bash
cd <app-root>   # directory with src/index.ts
ww-cli login    # user; once
ww-cli init my-app --language typescript --auth custom
# edit src/**
ww-cli build && ww-cli validate
ww-cli invoke <action_key> --data test-data.json
# USER: bump package.json version, then:
ww-cli push --create    # first publish only
ww-cli push             # later bumps
ww-cli promote <semver>
```

Local `validate` is weaker than the server on `push`. Expect first push may 422 with `Unknown key` / `sample must be …` — fix in one pass.

## 3. Project structure

```
my-app/
├── package.json            # "name" = display name (brand casing!); "version" = semver
├── app.json                # generated by build — commit; never hand-edit
├── .whippyapprc            # app_id + app_version_id — COMMIT (no secrets)
├── README.md
├── assets/logo.png         # square ≥512, true-RGBA PNG
├── test-data.example.json  # placeholders only
├── test-data.json          # real creds — NEVER commit
└── src/
    ├── index.ts
    ├── authentication.ts
    ├── config.ts
    ├── lib/
    ├── creates/<key>.ts    # one handler per file; filename = key
    ├── searches/<key>.ts
    └── triggers/<key>.ts
```

- **One handler per file.** List/lookup actions that power dropdowns must live under **searches**, not creates.
- Import with `.js` extensions in TypeScript source (ESM).
- Align `src/index.ts` `version` with `package.json`.
- No Node builtins in `src/` (Worker runtime — see §4).

## 4. Runtime: `w` and `bundle`

Handler signature: `async (w, bundle) => result`. **Never import `w`.** **Never use raw `fetch`** — use `w.request`.

### `w`

| API | Role |
|-----|------|
| `w.request({ url, method, headers, body, params, multipart?, raw? })` | HTTP → `{ status, headers, data }` |
| `w.errors.*` | `ThrottledError` (429), `RefreshAuthError` / `ExpiredAuthError` (401 OAuth) |
| `w.console` | Worker logs |
| `w.stashFile` / `w.dehydrateFile` | File helpers (creates/searches/hydrators; not trigger subscribe handlers) |

### `bundle` (snake_case keys)

| Key | Contents |
|-----|----------|
| `input_data` | Form values (cleared fields may arrive as `"\n"` — treat as blank) |
| `auth_data` | Credentials |
| `meta` | Execution metadata (`execution_token`, `app_version_id`, flags, …) |
| `target_url` | Platform webhook URL for triggers |
| `subscribe_data` | On unsubscribe: value returned from subscribe |

### Worker = no Node APIs

Deployed code runs on **Cloudflare Workers**. Local invoke may polyfill Node — do not rely on that.

**Forbidden:** `Buffer`, `process`, `require`, `__dirname`, `node:*` imports.

**Use:** `TextEncoder` / `btoa` for base64, `Uint8Array`, `w.request`, Web Crypto.

### HTTP helper pattern

```ts
export async function vendorRequest(w: any, bundle: any, options: { path: string; method?: string; body?: unknown }) {
  const response = await w.request({
    url: `${API_BASE}${options.path}`,
    method: options.method ?? 'GET',
    headers: {
      Authorization: `Bearer ${bundle.auth_data?.api_key}`,
      Accept: 'application/json',
      ...(options.body !== undefined ? { 'Content-Type': 'application/json' } : {}),
    },
    body: options.body,
  });
  if (response.status === 429) throw new w.errors.ThrottledError('Rate limited; retry shortly.');
  if (response.status < 200 || response.status >= 300) {
    const detail =
      typeof response.data === 'string'
        ? response.data
        : JSON.stringify(response.data ?? {});
    throw new Error(`Vendor HTTP ${response.status}: ${detail}`);
  }
  return response;
}
```

Always include the vendor error body in thrown messages (users see that string in step tests). Reject any non-2xx — `w.request` returns error statuses as data rather than throwing.

## 5. Authentication

### API key → use `type: 'custom'`

```ts
export default {
  type: 'custom',  // NOT 'api_key' — scaffold api_key does not render Connect UI
  fields: [
    {
      key: 'api_key',
      label: 'API Key',
      type: 'string',
      required: true,
      help_text: 'Create keys in the vendor dashboard → Settings → API.',
    },
  ],
  // Never interpolate secrets (api_key) into connection_label — it is shown in the UI.
  connection_label: 'Acme',
  test, // cheap real call proving the key works
};
```

`init --auth custom` is preferred. Auth fields: effectively `string` | `password` | `boolean`; use `help_text` (not `description`); no `choices` on auth fields. Prefer a static or non-secret `connection_label` (account name / email), never the API key.

### OAuth2

User must create a vendor OAuth app and register **Whippy’s** callback URL (confirm current production callback with Whippy — typically under `https://workflows.whippy.ai/...`). Store `client_id` / `client_secret` via `ww-cli secrets` (user). Agents must list OAuth prerequisites early and not claim the app is fully testable until those exist.

## 6. Actions and fields

### Shape

```ts
export const findEmail = {
  key: 'find_email',           // immutable once shipped
  noun: 'Contact',
  display: { label: 'Find Email', description: '…' },
  operation: {
    input_fields: [ /* … */ ],
    perform,                   // async (w, bundle) => …
    sample: { /* see contract */ },
    output_fields: [{ key: 'data', label: 'Contacts' }],
  },
};
```

### Output contract (server-enforced on push)

| Kind | `perform` returns | Built `sample` shape |
|------|-------------------|----------------------|
| searches | **array** of row objects | `{ data: [ row ] }` |
| creates | **single object** | `{ data: { … } }` |

In **source** `.ts`, prefer raw row/object samples; `ww-cli build` wraps under `data`. Do not double-wrap (`data.data`).

Use real documented example responses (or live captures) — never invent filler `{ id: 'example' }`. Unwrap vendor envelopes the same way `perform` does. Creates should return the useful record (id, url, status), not only `{ success: true }`.

### Push-safe `input_fields`

| Need | Use | Avoid on push |
|------|-----|----------------|
| Select | `type: 'string'` + `choices: { value: 'Label' }` | `type: 'select'`; array `choices` |
| Multiselect | string + `choices` + `choices_multiple: true` | `type: 'array'` |
| Nested rows | `type: 'text'` JSON + example if array 422s | Assume `array` always pushes |
| Help | every field has `help_text` | missing help; `description` on auth |
| Labels | ≥ 3 characters | `Id`, `To` |

`choices` **must** be `{ submittedValue: 'Label' }` objects — arrays submit indexes.

Every field needs useful `help_text`. Prefer dynamic dropdowns for IDs (`dynamic: 'list_things.id.name'` pointing at a **search**). Defaults are **strings**.

### Coverage best practice

When the vendor publishes OpenAPI/Swagger, inventory endpoints and ship the actions users need for real workflows (not only the smallest happy path). Document intentional skips with a reason. Prefer human-friendly inputs (names via dropdowns, relative dates) and convert to vendor formats inside `perform`.

## 7. Triggers (short)

- Implement subscribe / unsubscribe / (optional) list for samples.
- Register the platform `bundle.target_url` with the vendor.
- Sample = real webhook event body, **not** the subscribe ACK.
- Skip account-wide webhooks with no subscribe-time scoping (every workflow would fire).

## 8. Deploy

- **First push:** `ww-cli push --create` (writes `.whippyapprc`). Commit that file.
- **Later:** plain `ww-cli push`. Confirm output says `Using existing app ID`.
- If `--create` creates the app then validation fails: fix and **plain `push`**, do not `--create` again.
- `promote <semver>` publishes. Workflow steps **pin** to `app_version_id` — after promote, re-add the app step in test workflows.
- Logo: `ww-cli logo assets/logo.png --color '#RRGGBB'` (square ≥512 RGBA PNG).

## 9. Testing

```bash
cp test-data.example.json test-data.json   # gitignored secrets
ww-cli invoke authentication.test --data test-data.json
ww-cli invoke find_email --data test-data.json
```

Also run a builder **Step test** after promote. `Worker returned 500` usually means your code threw (check thrown message / `console_logs`).

## 10. Top gotchas

1. Cleared fields arrive as `"\n"` — omit blank params.
2. Auth `type: 'api_key'` → no Connect form; use `'custom'`.
3. Server validator > local validate.
4. Searches return arrays; creates return objects.
5. First push `--create` once; commit `.whippyapprc`.
6. Steps pin to versions — re-add after promote.
7. Dynamic dropdowns only call **searches**.
8. `choices` arrays submit indexes.
9. Stale `api_url` in `~/.whippyrc` sends traffic to the wrong host — re-login to production if pushes 404.
10. No `Buffer` / Node APIs in Worker code.
11. Don’t pre-wrap samples under `data` in source.
12. Action `key`s are forever (rename = new key).

## 11. Handoff checklist (agent → user)

```bash
ww-cli build && ww-cli validate
# auth type custom|oauth2; samples/output_fields sane; no forbidden field keys
ww-cli invoke <smoke_action> --data test-data.json
# bump package.json + index version
```

Tell the user: app path, version, what to push/promote, and that agents did **not** deploy.
